Centralized App platform

80 users a month

Hundreds of accounts reach 15–20 internal analytics apps through one sign-in, instead of a scattered set of links.

Live. I set up the server, containerized every app on it, and run the platform.

The problem

Internal analytics apps were scattered across separate links. There was no shared way to give people access, track usage or deploy, so finding the right app meant knowing the right link.

Version control was limited or absent, so there was no common record of how each app changed.

What I owned

The whole SDLC. I set up the self-hosted server, containerized every app it hosts, and configured ShinyProxy, including who can open which app. I also introduced the Git workflow, built the monitoring app and set up weekly database backups.

How it works

One sign-in, access by group

Everyone signs in once to ShinyProxy and sees the apps their group is allowed to open. Group access for every app lives in one configuration, so access is managed in one place.

Containers only while someone is working

Each of the 15–20 apps runs in its own container. When someone opens an app, ShinyProxy has Podman start its container. After the user logs out or goes inactive, the container stops, so idle apps hold no server resources. The most-used apps keep warm containers ready, so they open without the usual start-up wait.

Shared containers for busy read-only apps

Frequently used read-only apps run in a shared container. Concurrent users of one of those apps share a container instead of each starting their own to reduce resource usage.

Decisions

Warm containers for the busiest apps

Starting every app on demand saves server capacity, but people wait while the container starts. I monitored which apps were used most and gave those warm containers through ShinyProxy’s pre-initialization feature.

Trade-off. A warm container holds resources even when no one is using it, so I keep them only for the busiest apps. The rest still use nothing when idle.

Share containers only for read-only apps

One container per user is the safe default, but it multiplies load when many people open the same app. For frequently used read-only apps, I let concurrent users share one container.

Trade-off. Sharing is only safe when one user cannot affect another, so I share containers only for read-only apps that hold no state between users, and Shiny keeps each user’s session separate on the app’s server. Sharing has caused no problems so far.

Evidence

  • 300 provisioned accounts
  • 80 users a month
  • 15–20 containerized apps hosted
