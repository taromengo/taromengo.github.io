Mengo

My personal software factory

Built to answer one question: how do I leave a coding agent running and still trust and evaluate what it did? Mengo splits a spec into small tickets. One agent implements each ticket test-first, checks I set beforehand decide whether it passes, a second agent reviews it, and each ticket ends as one local commit I can read on its own.

A working OMP (Oh My Pi) plugin, to be open-sourced soon.

The question

My own work kept raising one question: how do I run an always-on agent that I can trust and evaluate? Left alone on a whole feature, a coding agent can go in circles for a long time as its context fills, then return one change too large to review properly. Prompting it after every step avoids both problems, but then I sit at the keyboard for the whole job and the agent never runs on its own.

The question has two parts: how can I trust an agent I am not watching, and how do I avoid context rot?

I took inspiration from Matt Pocock, Uncle Bob and Lauren Tan’s approach to agentic workflows and built mengo on it. I write the spec, tickets and acceptance criteria through a grilling session, set the checks, then start a mengo run and leave it. Agents work through the spec one ticket at a time without prompting, with reviewer agents checking along the way, and the run stops only when every ticket is committed or it needs me.

How it works

The checks, the repair budget, reviewer agents and the pause let me trust an "AFK" run. The per-ticket commits and the records under .mengo/ are what I evaluate afterwards.

Write the plan

A spec describes the change. Its tickets break it into numbered tasks, each with acceptance criteria written as Markdown checkboxes. /mengo init finds the project’s specs, test commands and Python, asks about what it can’t infer, such as which models to use, and writes a commented mengo.toml.

Tracking for regression

Before any agent works, mengo runs every configured check once to see what already fails and records a baseline for comparison. Checks that were already failing, and checks marked optional, are reported but don’t block. Each finished ticket’s results become the starting point for the next.

Implement and check

An agent is called through omp-rpc and reads the ticket and changes the code test-first, using a configurable TDD skill. Its last message is saved as its report. mengo then runs the checks. If a required check passed at the start of the ticket and fails now, the implementer gets the end of the log, the path to the full log and an instruction to fix the cause. It may change a test only if the test itself is wrong, and has to say why.

To prevent infinite loops, every repair spends a round from a budget both agents share, three per ticket by default.

A second agent reviews

A separate reviewer session, using a configurable review skill, checks the change against the ticket’s acceptance criteria and the repo’s coding standards. It looks at test changes and new dependencies, and fixes problems itself. The same model can fill both roles, or each can have its own. If the reviewer changes anything, the baseline checks run again and the reviewer repairs any new failure.

Commit, or pause

When the checks allow it, mengo ticks the ticket’s checkboxes and makes one local commit named after it. If the repair budget runs out, the run pauses with the failing check, its log and the command to continue.

Progress, check logs and agent sessions are saved under .mengo/, so a run can be stopped and resumed seamlessly, and I can see what happened when something needs attention. A separate mengo skill lets an agent that starts with no context read those records and explain a pause, a stalled or failed run, or an error message, so debugging a run doesn’t depend on my memory of it.

Decisions

Each change of direction has a short decision record. These four shaped mengo most.

Judge the work by checks, not agent reports

Early versions asked agents to record and cite their own check results. Runs kept getting stuck on that bookkeeping, so the controller now runs the checks itself and compares them with the baseline. Runs no longer get stuck this way.

Trade-off. Checks are compared by name, so a new failure inside a check that was already failing can go unnoticed.

The reviewer repairs but cannot veto

The reviewer fixes what it finds instead of submitting a verdict. Only I can keep a ticket whose checks fail, with /mengo accept, and that override is recorded in the commit.

Trade-off. Quality depends on how well the checks cover what matters, and problems that span several tickets need a look after the run.

Dropped LangGraph for the standard library

LangGraph added 38 packages and 85 MB to run a fixed sequence the controller can call directly. The controller now runs on Python 3.11 or newer with nothing to install or download.

Trade-off. An OMP session left open across that update needs a restart.

Made the sandbox optional

The old Docker sandbox needed rebuilding for every update, so it was often skipped. A separate native plugin now confines every agent’s shell commands, and mengo behaves as before when it is off.

Trade-off. It guards against mistakes, not a determined attacker: files outside the deny list stay readable.

Evidence

I run mengo regularly and have used it on more than 10 specs. Six decision records give the problem, decision and trade-offs behind each change, including two I later overturned. A bundled three-ticket practice project lets a new user watch the whole loop on a small Hello, world! program.

How far to trust it. mengo is a personal tool in a private repository, so the evidence is my own use, not outside adoption.
