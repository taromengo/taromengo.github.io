Agentic RAG assistant

Used by teams across APAC

Staff ask questions about sensory methods and get answers drawn from 800–1,000 pages of technical literature and internal documents, with the sources shown.

Live. I designed, built, evaluated and deployed it, and I support it in production.

The problem

Sensory methods were scattered across long technical literature, internal documents and legacy slide decks. New colleagues had to find them for the first time, and busy ones had to recall them quickly.

The material comes in three kinds: textbooks, internal knowledge (including the slide decks) and a third type of document. A single retriever over all of it often returned chunks from the wrong kind, so I split it into three knowledge bases.

People also describe products in everyday words, while the team works in a fixed sensory vocabulary, its lexicon. New joiners don’t know the lexicon yet, and experienced colleagues still need to recall which terms fit, so a useful answer often needs that translation too.

What I owned

All of it. I designed, built, evaluated and deployed the assistant, and I support it in production. That covers the LangGraph flow, the retrieval pipeline, the Shiny for Python interface, the evaluation set, the tracing and the Podman container it runs in.

The search models run on a local inference stack, which I also set up and which has its own case study.

How it works

Clarify and route

A clarifier reads the question and, when context is missing, asks follow-up questions and waits for the answers. It writes what it learns into structured fields in the graph’s state. Later steps read those fields, and the clarifier uses them to send the question to one of three retrievers, so each search stays inside one kind of document.

Retrieve

Each retriever has its own knowledge base and runs the same pipeline: BM25 keyword search and vector search, then a cross-encoder reranks the combined results.

The embedding model and the reranker run on a local GPU, behind one OpenAI-compatible endpoint. The app sends a warm-up request when it opens, so the 40–60 second model load happens before the first question instead of during it to reduce user-perceived latency.

Answer

The generator drafts an answer from the reranked chunks. When the draft needs more, it calls the retriever again with a rewritten or expanded query. Every answer lists the documents it drew on, so people can check the basis before they rely on it.

A separate lexicon search, also reachable from the chat with a slash command, combines embeddings with keyword search to map everyday descriptive words to the team’s lexicon.

Evals

Self-hosted Langfuse traces every run. An LLM judge reads the question, the retrieved chunks and the answer, and labels the answer grounded, somewhat grounded or not grounded; it asks three different models and combines the results. Users can rate answers with a thumbs up or down, stored next to the trace. Together they show when answers go wrong, without relying on anecdotes.

Decisions

Removed the evaluator agent

An earlier version had an LLM agent that judged each retrieved chunk before generation. It sounds good in theory, but it added extra model calls. So I tested whether it earned them: three pipelines on the same questions, shown under Evidence. Taking it out (pipeline 1 to 2) left retrieval about where it was, so I removed it. A cross-encoder reranker (pipeline 3) then gave the gain.

Result. Removing it took its LLM calls out of every query, cutting latency and token cost. The lesson I took: a cheaper, deterministic component beat an extra LLM step, so measure before adding agents.

Routed each question to one knowledge base

One retriever over mixed sources kept returning chunks from the wrong kind of document. Rather than ask users to know where information lives, the clarifier now routes each question for them.

Local models for search, an API for answers

Embedding and reranking run on local hardware, so they carry no per-call fee. The generator and the judge run on an API, because writing and grading answers is where a frontier model earns its cost.

Trade-off. The API step sends the question and the top-ranked passages outside the network, and the provider sets the price. I accepted that for the two steps where model intelligence matters most in the pipeline.

Removing the evaluator agent (pipeline 1 to 2) left precision@8, recall@8 and nDCG@8 at about 0.6. Swapping ColBERT for a cross-encoder (pipeline 2 to 3) raised each to about 0.7.

How far to trust it. The set is 72 synthetic, LLM-labeled questions, written by an LLM in the voices of three personas derived with Ragas. Questions written from the documents reuse their wording, so the absolute scores likely run high; the comparison between pipelines is the result that matters.

What users say. Stakeholders say methods and the team’s lexicon are now easier to find, and that the assistant gives a quick overview of which sensory test protocols are available and which lexicon to use for a project.
